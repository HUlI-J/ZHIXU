# 知序 · 发布与自动更新运维手册

更新日期：2026-11-18。本文面向维护者，说明当前代码提交、审核、发布与验证流程。

## 1. 代码提交与审核

1. 从最新 `origin/main` 创建工作分支，提交代码和对应 README、操作手册的更新。
2. 只提交源码、配置和公共文档。数据库、附件、API Key、网页密码、GitHub 凭据、个人日志、依赖缓存和安装产物不进入代码 PR。
3. 执行类型检查、生产构建及相关测试，在 PR 中写明实际验证结果。
4. 推送工作分支，创建以 `main` 为目标的 PR，完成审核后合并。
5. 需要正式发布时，在经过审核的变更中同步 `package.json` 与 `package-lock.json` 的版本号，准备对应发布说明。未完成审核的工作分支不直接发布正式 Release。

## 2. GitHub Actions 发布（推荐）

合入 `main` 后，在 Actions 运行 **Release Desktop**：

- 分支选择 `main`。
- `version` 填写与 package.json 一致的版本号，不带 `v`。
- `notes_path` 填写仓库中实际存在的发布说明路径，例如 `docs/<版本>发布说明.md`；不要沿用不存在的模板路径。

流水线使用 Node.js 24，执行依赖安装、Windows 构建打包、资源校验、Release 创建与更新源复核。工作流文件为 `.github/workflows/release.yml`。手动触发工作流本身不等于完成 PR 审核，维护者需要先确认来源提交已经审核合入 main。

## 3. 本地发布方式

在 Windows 项目根目录，确认代码已经审核合入 main，且版本和发布说明准备完毕后执行。将 `$NotesPath` 改为本次实际发布说明；显式传入版本与说明路径，避免沿用脚本的旧版本默认值：

```powershell
npm ci
npm run dist
$ReleaseVersion = (Get-Content package.json -Raw | ConvertFrom-Json).version
$NotesPath = 'docs/本次发布说明.md'
powershell -File scripts/publish-release.ps1 -Action create -Version $ReleaseVersion -NotesPath $NotesPath
powershell -File scripts/publish-release.ps1 -Action upload -Version $ReleaseVersion -NotesPath $NotesPath
powershell -File scripts/publish-release.ps1 -Action publish -Version $ReleaseVersion -NotesPath $NotesPath
powershell -File scripts/publish-release.ps1 -Action verify -Version $ReleaseVersion -NotesPath $NotesPath
```

凭据使用发布环境的授权方式提供，不写入仓库。出现失败时先运行 `powershell -File scripts/publish-release.ps1 -Action status -Version $ReleaseVersion -NotesPath $NotesPath` 检查实际状态，避免重复发布或遗漏资源。

## 4. 必需发布产物

对版本 `<版本>`，正式 Release 应包含：

- `Zhixu-<版本>-Windows-Setup.exe`
- `Zhixu-<版本>-Windows-Setup.exe.blockmap`
- `latest.yml`
- `Zhixu-<版本>-source.zip`
- `SHA256SUMS-<版本>.txt`

上传前确认版本一致、文件完整，并核对 SHA-256 清单和 latest.yml 中安装包的 SHA-512。源码包需排除数据库、附件、凭据、node_modules、临时文件和缓存；构建产物通过 Release 交付。

## 5. 自动更新与发布后复核

桌面端匿名访问 `https://api.github.com/repos/HUlI-J/ZHIXU/releases/latest`，读取正式 Release 的 `latest.yml`，发现更高版本时下载并校验，之后由用户确认重启安装。草稿、预发布或只有 tag 的提交不等于可用的正式更新。

发布后检查：

1. Release 已正式发布，标题和说明正常显示，版本及目标提交正确。
2. 五项资源齐全，文件大小及散列正确，下载的 latest.yml 与安装包一致。
3. releases/latest 返回本次正式版本，客户端可发现更新。
4. 在隔离测试数据上安装、启动、重启，检查数据持久化与改动功能。
5. 确认更新没有改变用户数据位置，旧数据与附件仍能读取。

## 6. 常见问题

- **客户端看不到更新**：检查 Release 是否仍为草稿、是否为预发布、版本是否更高，以及 latest.yml 是否存在。
- **资源上传失败或不完整**：检查发布日志、授权与网络，再核对资源状态、大小和散列；不要先宣告发布成功。
- **版本不一致**：同时核对 package.json、package-lock.json、tag、Release 和 latest.yml。
- **标题乱码**：脚本和发布说明使用 UTF-8，Windows PowerShell 5.1 的脚本文件需注意编码识别。
- **网络失败**：检查系统代理或 HTTPS_PROXY / HTTP_PROXY，保留失败信息并重试；不要以关闭校验代替处理网络问题。
